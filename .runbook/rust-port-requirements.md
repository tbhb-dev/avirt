# Rust port requirements

Requirements for replacing `claude-container` and `codex-container` (TypeScript) with Rust. Sources: the fixes already applied to `claude-container/src`, the same fixes ported to `codex-container/src`, and a triage of the agy review in `scratchpad/agy-codex-review.txt` (each finding checked against the code). Items marked (both) apply to both experiments, (codex) only to codex-container.

## Requirements carried from both reviews

Behaviors already implemented in the TypeScript that the Rust port must preserve:

- (both) The daemon serves cleartext HTTP/2 with `POST /launch` and `POST /sessions/:id/stream`. (Changed by the egress work: `/launch` is on `127.0.0.1:<port>` only, for the CLI, and the stream route is served per session over a Unix socket the daemon dials, see the section at the end.)
- (both) Prompts reach the container via `-e NAME` with no value so they never appear on argv, and no secret is ever on argv.
- (both) Every daemon stream has an `error` listener, the server has a session-error handler, and `reply()` returns early if the stream is closed or destroyed.
- (both) A stream ends on either `end` or `close`, because an aborted stream (RST_STREAM, killed container) never emits `end`.
- (both) On stream end the daemon flushes the trailing partial line and the decoder's remaining bytes into the log.
- (both) Sessions live in a map keyed by an id redrawn on collision, and a second stream POST for the same id gets 409.
- (both) `container_exit` is written only after the stream has closed (or immediately if no stream was ever accepted), so it is always the last log line; `container_error` is written immediately.
- (both) `/launch` rejects a non-absolute `cwd` with 400 and a missing prompt with 400.
- (both) Errors are logged with their stack, not as a raw error object (which may echo secrets).
- (both) The entrypoint's uplink close is a no-op wait if the request is already closed, and the h2 client session has a permanent error listener (the CLI too).
- (both) The entrypoint waits for the agent process to be fully gone and its output drained before ending the uplink, and the whole ACP session is raced against agent death so a dead agent cannot hang pending calls.
- (both) The tap is byte-transparent: bytes pass through unchanged and each complete line is also reported as an envelope `{ts, dir, msg}` with `dir` in `client->agent`, `agent->client`, `meta`; unparseable lines are kept as `{raw}`. Meta events keep their current names (`start` (now with an `agent` field), `agent_stderr`, `auto_approve`, `error`, `exit`, `container_exit`, `container_error`, plus `auth_methods` and `auth_writeback` for codex).
- (both) Permission requests are auto-approved: first `allow_once`, else `allow_always`, else the first option, else cancelled.
- (both) The CLI `--follow` parses each log line as JSON and stops only on a meta `container_exit` or `container_error`, never on a regex over raw text.
- (both) Image is `ubuntu:26.04`, non-root `agent` user, workspace `/workspace`; defaults are claude 8787 and codex 8788 with separate image names so the daemons coexist.
- (codex) ACP is v1 (codex-acp 2.2.2 hardcodes version 1); claude uses v2 with `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1` and `protocolVersion: 2`. Pins stay exact.
- (codex) No `authenticate` call, because the adapter's `chat-gpt` authenticate forces a token refresh on every launch.

Requirements from the triage of review findings:

- (both) The daemon handles SIGINT and SIGTERM: stop running containers, wait for each to exit, run the per-session cleanup (write-back for codex, temp dir removal), then exit. Also clean up if setup fails partway (log open or spawn fails after the temp dir exists). Verdict real; claude has no temp dir but its `--rm` containers would otherwise keep running with no log sink.
- (both) Log directory is created 0700 and every log file 0600, since logs hold prompts, tool output and, if the agent reads it, credentials. Verdict real (defaults were 0755/0644).
- (both) Delete a session's state once its exit note is written and its stream has drained, and refuse a later stream POST for an exited session (410). Verdict partly real: the map leak is real, and in codex the closure also retains the plaintext `auth.json` seed; the duplicate `container_exit` needs an unlikely in-flight race. In Rust, drop the seed as soon as cleanup finishes.
- (both) The entrypoint bounds its wait for the agent to exit: send termination, wait a few seconds, then kill, and treat EOF on the agent's stdout as authoritative before declaring failure. Verdict partly real: Node's `close` waits on any grandchild that inherited the pipes, and `exit` can fire before stdio drains, truncating the last lines. The same code exists in claude-container.
- (both) After the agent dies, drain remaining stdout and stderr to the uplink before reporting the failure, and make sends after the uplink is closed no-ops instead of errors.
- (both) The entrypoint checks the HTTP status of the stream POST response and fails fast on 404 or 409 instead of running the agent into a dead stream. Verdict real but minor.
- (both) The daemon's request-body reader fails on stream `close` as well as `error`, so an aborted `/launch` does not leak a pending handler. Verdict real but minor.
- (both) The entrypoint verifies the `protocolVersion` in the initialize response equals the one it sent, and fails clearly otherwise. Verdict partly real: cheap and the spec expects it.
- (both) `--cwd` semantics must be decided and enforced. Today `SESSION_CWD` is passed into the container but never mounted, so any path other than the in-image `/workspace` does not exist there and `session/new` fails. Verdict real. Recommended: treat `cwd` as a path inside the container, reject anything outside `/workspace`, and add an explicit separate opt-in for mounting a host directory.
- (codex) Consume session updates concurrently with the prompt request instead of awaiting the prompt first. Verdict partly real: in v1 the `session/prompt` response only arrives at turn end, so awaiting it first delays console output until then and, if the prompt rejects, the queued updates are never shown (the SDK queues an error after them but the awaiting code throws first). The NDJSON log is unaffected because the tap is below the SDK. claude-container uses v2 where the response is an acknowledgement, so it is not affected; the Rust code should still handle both shapes by driving the update stream and the prompt future together.

## Codex-specific auth requirements

- The daemon reads the host `auth.json` per launch and writes it to a unique temp directory (0700) as a 0600 file; the directory is mounted at `/codex-home` with `CODEX_HOME` set. Nothing goes in the image, argv or env. No host `config.toml` is copied.
- Cleanup (write-back, then temp dir removal) runs exactly once on every path: normal exit, container kill, spawn error, setup failure, and daemon shutdown.
- Write back when the container's `last_refresh` is newer than the host file's current `last_refresh`, not only when the host still equals the seed. Verdict on finding 1: real. The strict-equality guard drops a legitimately rotated token whenever another session or the host Codex wrote first, which leaves a spent refresh token on disk. Compare against the host's current content, keep the container copy only if strictly newer, and report "host newer" otherwise.
- Serialize write-backs with an exclusive lock (flock on a sidecar lock file) so the read-compare-replace sequence cannot interleave across sessions or daemons.
- Concurrent sessions that start from the same stale refresh token cannot both refresh, because the token is single-use. Either serialize launches while the access token is stale or accept and document that the loser fails; the finding is real but inherent to per-session copies.
- Replace the host file atomically: write to a uniquely named temp file in the same directory created with exclusive-create and mode 0600, fsync, then rename. Do not use a fixed temp name.
- Keep only the first backup (`auth.json.pre-acp-backup`), created exclusively and never overwritten. Verdict on finding 5: real; the current code overwrites it on each write-back, so after two rotations it holds a spent token.
- Before reading the session's `auth.json`, open it with no-follow semantics and refuse anything but a regular file; cap its size and require it to parse as JSON with a valid `last_refresh` and the same `auth_mode` as the seed. Verdict on finding 3: real, since the agent has write access to the mounted directory and can swap in a symlink the host would follow.
- Never log or return parse errors that may quote auth content; log only a fixed reason string.
- Document that the agent sees `CODEX_HOME` and, with auto-approve, can read `auth.json` into the log and container output, and that logs contain the account email and plan.
- Forward `INITIAL_AGENT_MODE` to the container as today; codex-acp reads it from its own environment.

## Rejected findings

- Finding 11 (`INITIAL_AGENT_MODE` is never applied and codex-acp configures modes only through `session/set_mode`): not real. codex-acp 2.2.2 reads `INITIAL_AGENT_MODE` from its environment at startup (valid ids `read-only`, `workspace-write`, `agent`, `agent-full-access`), and the README documents it. A run with `read-only` produced a `session/request_permission` that was auto-approved.
- Finding 2's claim that `spawn` commonly throws synchronously: not real for spawn itself, which reports failure through the `error` event; the part about `openSync` or the writes failing after the temp dir exists is real and is kept above.
- Finding 8's claim that queued updates are lost on a successful prompt: not real, they are drained; only the prompt-rejects case and the display delay are real, as noted above.
- Finding 10's claim that a duplicate `container_exit` is likely: not real as stated, since it needs a stream POST arriving after the container already exited; only the leak and the retained seed are kept.

## As built in the Rust port

Where the Rust port differs from the requirements above, deliberately:

- `agent_exit` is dropped. The entrypoint uses the SDK's `AcpAgent`, which owns the adapter process and does not report its exit status; a crash surfaces as an `error` event carrying the SDK's message (including a stderr tail for a nonzero exit). The bounded teardown is the SDK's: after the protocol ends it waits up to 1 second for the adapter to exit, then SIGKILLs its whole process group (there is no SIGTERM step), and it races the protocol against adapter exit so a dead agent cannot hang pending calls. Protocol lines are all reported before the session returns, but stderr bytes still unread when the adapter exits cleanly can be lost, because the SDK stops reading stderr then and its API offers no drain hook.
- `--cwd` means a host directory, not a container path. The daemon bind-mounts it read-write at `/workspace` (`-v host:/workspace`) and sets `SESSION_CWD=/workspace`. It must be an absolute path to an existing directory and must not contain `:`, which would break the mount spec; anything else is a 400. Only an explicit `--cwd` mounts anything, which is the opt-in; without it the agent gets the image's empty `/workspace`.
- The two daemons are one (`acpd`). Credentials are checked per launch, not at startup: a claude launch without `CLAUDE_CODE_OAUTH_TOKEN` or a codex launch without `auth.json` returns 400 with a message.
- The container has no network (`--network none`), so the uplink is no longer a TCP connection from the container to the daemon. The per-session supervisor listens on `session.sock` and `proxy.sock` (host mode 0600, in a private 0700 directory) and the daemon mounts both into the container as socket files (`-v`); the supervisor dials the daemon's own socket (private directory, mode 0600) and splices the uplink to it at L4, so HTTP/2 stays end to end between the entrypoint (client) and the daemon's `/sessions/:id/stream` handler (server). Each supervisor connection starts with a line naming its kind and session (`SESSION <id>` or `EGRESS <id>`), and a session's connection can only post that session's own stream. The gateway lookup and the `0.0.0.0` bind are gone. The requirements about stream states (404, 409, 410), draining, `container_exit` ordering and the stream route's behavior still apply.
- The entrypoint connects to `session.sock` with timeouts (a listener that is gone but whose socket file remains accepts a connect and then hangs) and starts neither the proxy relay nor the agent until the daemon has accepted the stream; it fails fast with a message naming the supervisor otherwise. The agent's environment is built by the entrypoint and contains neither the session id nor the prompt, and `DAEMON_URL` is gone from the container's environment.
- Teardown order on every path: container exit, then supervisor stop and drain, then the daemon-side event connection's EOF, then the cleanup note and `container_exit`, then removal of the session directory. A supervisor that dies while the container runs gets a `container_error` and the container is stopped.
- A new `dir: "egress"` envelope carries the per-connection events of the session's proxy (see `.runbook/egress-design.md`), and `start` carries the `agent`.
- Each session has a random uplink token, known only to the daemon and the entrypoint (`ACP_UPLINK_TOKEN`, stripped from the agent's environment). The stream POST carries it in `x-acp-token`; a wrong or missing token gets 403 before the session's state changes. The entrypoint applies a seccomp filter denying `socket(AF_VSOCK)` before it starts the agent, and the container runs with `--init`; the entrypoint handles SIGTERM by ending the session cleanly. See "Threat notes" in `.runbook/egress-design.md`.
- All on-disk session state (session directories, the daemon socket, Codex temp homes) lives under one state root, `$TMPDIR/acpd-<uid>/` (0700). `acpd serve` takes an exclusive lock on it for its lifetime (a second instance exits with an error) and, before listening, sweeps what a previous daemon left: containers labelled `acpd=1` are stopped and deleted, directories are removed (made removable first; a failure is logged, not fatal), and nothing is written back to the host. This supersedes the "cleanup also runs if setup fails partway" caveat for the SIGKILL case, which no in-process cleanup can cover.
- A line longer than 16 MiB is dropped whole and replaced by a daemon-authored `line_truncated` meta event, on both the entrypoint and the daemon side. `container_exit` is always the last event of a session; errors (`container_error`) are held and written before it, including when the container could not be started, and `acpd launch --follow` stops only on `container_exit`.
- A Codex write-back additionally requires the same top-level keys, `auth_mode` and account identity as the seed and a `last_refresh` at most 5 minutes in the future. When the container cannot be confirmed gone after stop, kill and delete attempts, cleanup and write-back are skipped (the temp home is left for the next sweep) and a `container_error` says so.
- `container run` and `acp-supervisor` start from a cleared environment; the supervisor's secret is in its environment only and is checked on both of its daemon-socket preambles, with a single event connection per session.
